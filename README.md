# CXR LDC Eval

CXR LDC Eval is a deterministic, configuration-driven implementation of Longitudinal Disease-Change (LDC) evaluation for chest X-ray VQA answers. It compares generated answer text with reference answer text after converting both into normalized disease-change claims.

## What is included

- CPU-only, Python standard-library evaluation code
- A versioned 31-label ontology, aliases, hierarchy, transition mappings, and evaluation profiles
- Exact and hierarchical LDC metrics for three separately reported ontology views
- A generic JSON/JSONL interface independent of any dataset or model
- A legacy adapter for existing COCO-style merged prediction/ground-truth files
- Synthetic examples, tests, protocol documentation, and a GitHub Actions workflow

No images, clinical rows, patient/study identifiers, dataset files, model weights, checkpoints, prediction artifacts, or raw evaluation outputs are included.

## Install and run

From this directory:

```bash
python -m pip install -e .
ldc-eval validate-config
ldc-eval records \
  --input examples/synthetic_records.jsonl \
  --output-dir /tmp/cxr_ldc_demo \
  --output-prefix synthetic
```

The module form is equivalent:

```bash
python -m cxr_ldc_eval --version
python -m cxr_ldc_eval records --help
```

The generic record format has four fields:

```json
{
  "id": "opaque-sample-id",
  "question": "What has changed compared to the reference image?",
  "prediction": "nothing has changed",
  "reference": "nothing has changed"
}
```

`question`, `prediction`, and `reference` are evaluated; `id` is used only for alignment and duplicate detection. Questions are required by default because routing changes the primary tuple. See [INPUT_FORMAT.md](src/cxr_ldc_eval/docs/INPUT_FORMAT.md).

## Paper-facing protocol

The primary metric is micro Exact LDC-F1 over query-aware normalized claims:

- Broad Difference/Change questions score `(entity, presence_transition)`.
- `NEW`, `RESOLVED`, and `PRESENT_BOTH` are the scored presence values.
- `WORSENED`, `IMPROVED`, `SAME_LEVEL`, and direction-unspecified level changes project to `PRESENT_BOTH` for broad Difference/Change questions.
- Level questions score `(entity, severity_transition)`.
- A `what has changed` question containing an anatomic location expression is intentionally routed to the Level profile. This project decision is config-driven and regression-tested.
- An explicit `WORSENED` versus `IMPROVED` mismatch remains a severity contradiction even when both claims project to `PRESENT_BOTH` for the broad primary score.
- Hierarchical scoring uses one-to-one maximum-weight bipartite matching.
- A metric with zero paper-facing denominator is serialized as JSON `null` and rendered as `N/A`, never interpreted as zero.

Report `cxr_primary` and `all_31_auxiliary` separately. The CheXpert-projected view is auxiliary/prior-work comparison only. Full definitions are in [METRIC_SPEC.md](src/cxr_ldc_eval/docs/METRIC_SPEC.md).

## Location-conditioned “what has changed”

This routing is deliberate and must remain stable for this release:

```text
What has changed compared to the reference image?  -> difference
What has changed in the left lung area?            -> level
```

The inspected valid/test query templates contained 362 location-conditioned rows; all 362 reference answers were Level-only, with exactly one entity claim per row. Aggregate evidence and placeholder-only answer forms are documented in [QUERY_ANSWER_TAXONOMY.md](src/cxr_ldc_eval/docs/QUERY_ANSWER_TAXONOMY.md). No source rows are redistributed.

This routing supersedes one location-routing statement in the earlier mapping guideline. The scoped amendment is recorded in [PROTOCOL_AMENDMENTS.md](src/cxr_ldc_eval/docs/PROTOCOL_AMENDMENTS.md), while the JSON config is the runtime source of truth.

## Outputs and privacy

A records run writes:

- `<prefix>_longitudinal_eval_v0_1_1.json`
- `<prefix>_longitudinal_eval_v0_1_1.md`
- optionally, `<prefix>_longitudinal_claims_v0_1_1.json`

Summary paths use a `<provided>` marker instead of source filenames, and input/config/document SHA-256 digests are recorded for provenance. Existing outputs are not overwritten unless `--overwrite` is explicit.

Claims JSON is not generated by default. The opt-in `--write-claims` artifact contains source question and answer text; keep it local and review it before sharing. A no-claims run refuses to leave a stale claims file for the same prefix.

## Legacy adapter

The `legacy` subcommand accepts COCO-style merged prediction and ground-truth JSON plus an optional generation manifest. It enforces unique IDs, exact prediction/ground-truth ID-set equality, and matching row indices when both sides provide them:

```bash
ldc-eval legacy \
  --pred-path predictions.json \
  --merged-gt-path ground_truth.json \
  --generation-manifest-path generation_manifest.json \
  --output-prefix run_name
```

The generic `records` interface is recommended for new integrations because it has no LLaVA, dataset, or model assumptions.

## Configuration

The bundled JSON is the source of truth for labels, aliases, ontology hierarchy, transitions, question routing, projections, contradiction pairs, and evaluation profiles:

`src/cxr_ldc_eval/config/cxr_longitudinal_eval_config_v0_1.json`

Do not hard-code new labels or transition mappings in Python. Any config change should update validation and regression tests.

## Test

```bash
python -m unittest discover -s tests -v
python -m py_compile src/cxr_ldc_eval/*.py
ldc-eval validate-config
```

The test suite uses only synthetic text and temporary files.

## Limits

This metric evaluates agreement between answer texts; it does not verify image grounding, clinical correctness, or temporal pairing by itself. Extraction is rule-based and currently strongest on the documented answer grammar. Unseen free-form language, negation, uncertainty, entity inheritance, and location descriptions require external validation before paper-facing use.
